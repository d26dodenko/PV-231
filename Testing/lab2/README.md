| 3 | DELETE `/booking/{id}` | 204 No Content | **201 Created** | **Особенность API**: удаление возвращает 201 вместо 204. Функционально объект удаляется, но расхождение с REST-семантикой. |
| 4 | POST `/booking` (`"totalprice":"abc"`) | 400 Bad Request | **200 OK** (создано) | **Дефект валидации**: API принимает строку в числовом поле без ошибки. Риск некорректных данных в хранилище. |

**Пояснения к классификации:**
- **Особенность API** — поведение стабильно воспроизводится, не ломает функциональность, но отличается от REST-стандарта. Фиксируется как наблюдение, серьёзность низкая.
- **Дефект валидации / обработки ошибок** — API принимает некорректные данные или отдаёт 500 там, где должен быть 400. Это реальные дефекты, оформлены баг-репортами.

## Баг-репорты

## BUG-01: 500 Internal Server Error при отсутствии обязательного поля

- **Шаги воспроизведения:**
  1. Выполнить `POST /booking`.
  2. В теле запроса убрать поле `firstname`, остальные поля оставить валидными.
- **Ожидаемый результат:** `400 Bad Request` с описанием ошибки валидации.
- **Фактический результат:** `500 Internal Server Error`.
- **Серьёзность:** Major — серверная ошибка вместо клиентской, усложняет диагностику.

## BUG-02: Принимается неверный тип данных в `totalprice`

- **Шаги воспроизведения:**
  1. Выполнить `POST /booking`.
  2. Передать `"totalprice": "abc"` (строка вместо числа).
- **Ожидаемый результат:** `400 Bad Request`.
- **Фактический результат:** `200 OK`, бронирование создано.
- **Серьёзность:** Major — нарушение целостности данных.

## BUG-03: Принимается отрицательная цена и некорректный период дат

- **Шаги воспроизведения:**
  1. Выполнить `POST /booking` с `"totalprice": -1`.
  2. Выполнить `POST /booking` с `checkout` раньше `checkin` (например, `checkin: "2026-11-01"`, `checkout: "2026-10-01"`).
- **Ожидаемый результат:** `400 Bad Request` в обоих случаях.
- **Фактический результат:** `200 OK`, данные сохранены.
- **Серьёзность:** Major — отсутствие бизнес-валидации.

## Выводы

В ходе лабораторной работы было освоено интеграционное и API-тестирование
на примере публичного учебного сервиса Restful-Booker. В Postman была
построена коллекция запросов с переменными окружения (`baseUrl`, `token`,
`bookingId`), настроена автоматическая передача токена и идентификатора
бронирования между запросами, а также написаны автотесты.

В результате прогона были проверены все эндпоинты, включая позитивную
цепочку, негативные сценарии, граничные значения и
различные коды ответов. Основным наблюдением стало существенное расхождение
фактического поведения API с REST-стандартом и документацией.

Таким образом, работа показала, что реальное API может значительно
отличаться от «идеального» REST как по кодам ответов, так и по строгости
валидации, поэтому тестирование должно опираться на фактическое поведение
сервиса, а расхождения — фиксироваться в отдельной таблице и оформляться
баг-репортами. Полученные навыки (построение коллекций, автоматизация
переменных, Collection Runner, анализ расхождений) применимы к тестированию
любых реальных REST API.
